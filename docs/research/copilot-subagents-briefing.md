# Copilot Subagents Research Briefing

## Executive Summary
Phase 3 shifts from discovery to operational readiness: we now have proof that the GitHub.com Agents tab telemetry (launch, monitor, steer, review) aligns with the VS Code Agent Sessions experience, giving program owners a single vocabulary for mission control regardless of where a task starts (FWP-023–FWP-026, FWP-044–FWP-045). This parity unlocks the upcoming Model Preference Matrix because we can evaluate model behavior against identical touchpoints in GitHub and VS Code without inventing tool-specific exception paths.

We also have the first official `#runSubagent` documentation to pair with the community’s worktree coordinator guardrails, so phase-aligned playbooks can recommend when to rely on Microsoft’s context-isolated subagents versus when to fan out into multi-model, multi-worktree experiments that still respect compliance review queues (FWP-043–FWP-045). The combination means side quests stay hermetic while long-running agent runs keep producing auditable logs.

Finally, the Plan agent, todo instrumentation, handoff metadata, and context-engineering workflow now have canonical coverage plus a reusable catalog (`github/awesome-copilot`) for cloning vetted agents, letting us feed Appendix A (Model Preference Matrix) and Appendix B (Context Packaging Playbook) with source-of-truth examples instead of bespoke lore (FWP-046–FWP-049).

## Phase 3 Synthesis Overview

### Agents tab vs VS Code Agent Sessions parity
A dual control-plane emerged this phase: the GitHub.com Agents tab governs cloud runs while VS Code’s Agent Sessions mirrors the same telemetry locally, so we can coach teams without splitting playbooks by surface (FWP-023–FWP-026, FWP-044–FWP-045).

| Surface | What you monitor | How to intervene | Unique actions |
| --- | --- | --- | --- |
| GitHub.com Agents tab | Session cards expose status, logs, diff previews, premium request usage, and review readiness for every delegated task (FWP-023–FWP-026). | Send steering prompts mid-run, stop/reset a session, or jump into VS Code Insiders for local edits via the Code button (FWP-023–FWP-026). | Assign custom agents per task, open the workbench overview, trigger **Approve and run workflows**, and keep branch-protection reviews centralized (FWP-023–FWP-026). |
| VS Code Agent Sessions | Side-bar view lists local chats plus background coding agents (Copilot coding agent, CLI, Codex) with live status and log streaming (FWP-044–FWP-045). | Open sessions as chat editors, send additional prompts, cancel stalled jobs, or delegate new work directly from the Chat view (FWP-044–FWP-045). | Run `#runSubagent` actions without polluting main context, hand off directly from Plan agent responses, and keep a single-pane view while hopping between tasks (FWP-044–FWP-045). |

### Context-isolated subagents and worktree safeguards
Microsoft’s guidance now codifies how `#runSubagent` creates context-isolated helpers that inherit only the baggage you explicitly forward, keeping main sessions lean while still exposing tool output in the Agent Sessions log (FWP-044–FWP-045). We pair that with the community worktree coordinator pattern, where each subagent spins up its own git worktree and branch so multi-model experiments never trample the primary checkout—ideal when you want GPT-5-Mini and Grok to race on the same brief without paying premium request costs (FWP-043).

Use the official subagent path for production delegations that need deterministic audit trails and VS Code governance; lean on the worktree coordinator when you need concurrent prototypes but can tolerate manual approvals for `git worktree` commands (FWP-043–FWP-045). In either case, scope tools to the task, document cleanup steps, and require reviewer acknowledgment before merging a subagent’s artifacts to stay within compliance expectations (FWP-043–FWP-045).

### Planning + context-engineering guardrails
Plan agent transcripts, auto-generated todo lists, and custom-agent handoffs now have official documentation, so our governance model can mandate that every complex request starts with plan → todo instrumentation before any edits ship (FWP-046–FWP-047). Microsoft’s context-engineering guide layers those planning assets with `.github/copilot-instructions.md`, implementation personas, and MCP tooling, which directly maps to the Context Packaging Playbook we owe in Appendix B (FWP-046–FWP-048).

To keep teams from reinventing primitives, we can source vetted `.agent.md`, `.prompt.md`, and MCP server configs from the `github/awesome-copilot` catalog, cite them inside the Model Preference Matrix, and note where we have to tune instructions for enterprise guardrails (FWP-049). The synthesis output from this phase therefore feeds both appendices: Appendix A will score models/agents against the parity table above, while Appendix B will document the planning + context stack that keeps those models within policy (FWP-046–FWP-049).

## Phase 2 Source Extraction Notes

### GitHub Docs – Managing Copilot coding agents (FWP-023)
- **Eligibility & entry points:** Feature is available to Copilot Pro/Business/Enterprise tiers, with the Agents tab (public preview) acting as a centralized command center for selecting repositories, base branches, and optionally assigning custom agents before issuing a task prompt ([FWP-023](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/manage-agents)).
- **Session monitoring:** Each session card surfaces live status; opening it reveals the session log and workbench so you can inspect the overview, diff, premium request usage, and session counts without leaving GitHub ([FWP-023](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/manage-agents#2-monitor-agent-activity)).
- **Steering while in-flight:** You can add clarifying prompts mid-run via the session log input to redirect Copilot without stopping the run—every steering message consumes one premium request ([FWP-023](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/manage-agents#3-redirect-agents-as-needed)).
- **Local follow-up:** The Code button in the session view lets you open the active task in VS Code Insiders (requires the latest GitHub Copilot + GitHub Pull Requests extensions) for hands-on edits ([FWP-023](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/manage-agents#4-open-an-agent-session-in-your-local-development-environment)).
- **Review & merge:** Once Copilot finishes, the workbench overview lists summaries and file diffs so you can jump into the pull request for final approvals, leveraging the linked reviewing guidance ([FWP-023](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/manage-agents#5-review-and-merge-agent-code)).

### GitHub Docs – Asking GitHub Copilot to create a pull request (FWP-024)
- **Omni-channel kickoff:** Copilot can be tasked from Issues, the Agents tab/panel, dashboard Task button, Copilot Chat across IDEs, GitHub CLI (`gh agent-task create` in v2.80+), GitHub MCP server (`create_pull_request_with_copilot` tool), Raycast, mobile, or the “New repository” form—ensuring the same underlying workflow no matter the entry point ([FWP-024](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/create-a-pr)).
- **Issue assignment flow:** When assigning an issue, you can provide optional prompts, constrain repositories/branches, and pick a custom agent profile so Copilot inherits repo-specific instructions before it branches and opens a PR ([FWP-024](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/create-a-pr#assigning-an-issue-to-copilot)).
- **Automation hooks:** GitHub CLI (`gh agent-task create/list/view`) and GraphQL mutations (`createIssue`, `replaceActorsForAssignable`) allow programmatic delegation after verifying `copilot-swe-agent` is available via `suggestedActors` ([FWP-024](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/create-a-pr#assigning-an-issue-to-copilot-via-the-github-api)).
- **IDE + MCP safeguards:** IDE workflows prompt you to include/ignore local changes, while MCP hosts require the GitHub MCP server plus explicit enablement of the `create_pull_request_with_copilot` tool before delegation ([FWP-024](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/create-a-pr#asking-copilot-to-create-a-pull-request-from-the-github-mcp-server)).
- **Monitoring + notifications:** Regardless of entry point, Copilot responds with the PR URL, works in the background, and adds you as a reviewer with notifications triggered in GitHub.com, IDEs, CLI, or Raycast; ongoing tracking routes to the session-monitoring doc ([FWP-024](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/create-a-pr#monitoring-progress)).

### OpenAI Docs – Function calling guide (FWP-029)
- **Five-step flow:** OpenAI frames tool calling as (1) describe tools, (2) receive model tool calls, (3) execute code, (4) append tool outputs, (5) get final response—keeping a running `input_list` through each step ([FWP-029](https://platform.openai.com/docs/guides/function-calling#how-it-works)).
- **Strict mode requirements:** Enabling `strict: true` forces adherence to JSON schema but only works if `additionalProperties` is false and every property is marked required (optionals use `null` in their type array) ([FWP-029](https://platform.openai.com/docs/guides/function-calling#strict-mode)).
- **Tool choice controls:** `tool_choice` can be `auto`, `required`, a forced function, or `allowed_tools` for subset restriction; `parallel_tool_calls` can be disabled to ensure serial execution ([FWP-029](https://platform.openai.com/docs/guides/function-calling#additional-configurations)).
- **Streaming tool calls:** Streaming surfaces `response.output_item.added`, `response.function_call_arguments.delta`, and `.done` events so you can accumulate arguments before executing the tool ([FWP-029](https://platform.openai.com/docs/guides/function-calling#streaming)).
- **Custom tools & grammars:** Beyond JSON functions, custom tools accept freeform strings and can be constrained with Lark or regex grammars when deterministic syntax is required ([FWP-029](https://platform.openai.com/docs/guides/function-calling#custom-tools)).

## Appendix B – Context Packaging Playbook

Appendix B brings together context layering, plan/todo instrumentation, Agent Sessions parity, and the Model Preference Matrix so every delegation reuses the same guardrails no matter which surface initiates the work (FWP-045–FWP-049). Because the GitHub Agents tab now mirrors VS Code Agent Sessions, these steps reference identical telemetry checkpoints on GitHub.com, VS Code, and downstream notebooks, letting planners port Appendix A judgments into actionable handoffs without duplicating evidence gathering (FWP-023–FWP-026).

### Step 1: Curate project-wide context
- Keep `.github/copilot-instructions.md` pinned to the latest architecture, product, and compliance attachments so agents inherit stable background knowledge before the Plan loop even starts (FWP-048).
- Bundle supporting docs (CONTRIBUTING, architecture primers, dashboards) alongside instructions so every agent session can cite the same anchors in GitHub.com or VS Code without re-uploading snippets (FWP-048).
- Align MCP policies and repository-level configs early—enterprise toggles plus repo `mcpServers` JSON must stay in sync so instruction references to official servers stay accurate across both coding agent and chat surfaces (FWP-040–FWP-041).

### Step 2: Plan with guardrails before delegating
- Invoke the Plan agent (or equivalent planner persona) to capture clarifying questions, scope notes, and research links before touching code, preserving those transcripts directly inside the session log (FWP-047).
- Convert approved plans into todo lists so VS Code Agent Sessions and GitHub Agents tab both reflect progress state, then gate implementation work on those checklist items to keep parity between cloud and IDE views (FWP-047, FWP-045).
- Attach handoff metadata (`handoffs` blocks inside `.agent.md`) so delegations from Plan → Implementer carry the prepared context packet, selected tools, and review expectations without manual copy/paste (FWP-046).

### Step 3: Implement with specialized agents
- Pick custom agent profiles tailored to the framework or risk domain, referencing curated `.agent.md` templates from the workspace plus community-sourced exemplars when the local catalog needs a jump-start (FWP-046, FWP-049).
- Use `#runSubagent` for deep research or experimental spikes so the main session stays lean while still logging subagent outputs for compliance review (FWP-045, FWP-044).
- When racing multiple models, lean on the community worktree coordinator or similar custom agents to spin isolated branches, letting planners compare outputs without overwriting each other’s artifacts (FWP-043).

### MCP integration & governance checklist
- Follow the agent-mode + MCP tutorial guidance to define clear goals, boundary prompts, and confirmation checkpoints before wiring tools into a session (FWP-039).
- Enable the enterprise MCP server policy (or confirm user-tier eligibility), then document the registry/manual install steps so GitHub.com and IDE clients share the same approved endpoints (FWP-040).
- Mirror repository-level `mcpServers` JSON into `.vscode/mcp.json` (or vice versa) whenever possible so coding agent runs and local chat sessions call the same toolchains (FWP-041, FWP-040).
- Map each MCP server to the Agent Sessions telemetry and GitHub Agents tab views so support teams know exactly where to monitor tool failures or long-running calls (FWP-044–FWP-045).
- Include rollout notes for Visual Studio, JetBrains, and mobile participants so parity guidance covers every supported workflow, not just VS Code Insider builds (FWP-044–FWP-045).

### RunSubagent & worktree escalation paths
Use VS Code’s context-isolated subagents whenever you need deterministic logs, scoped tools, and built-in cleanup prompts—the sessions remain traceable inside Agent Sessions and inherit only the context you forward (FWP-044–FWP-045). Switch to the community worktree coordinator pattern when you require simultaneous experiments or multi-model races, but insist that each subagent creates its own worktree/branch, reports risk factors (shell commands, validation gaps), and documents cleanup expectations before merging back (FWP-043–FWP-045).

### Linking back to Appendix A
Planners should combine Appendix A’s Model Preference Matrix with this playbook to select the right agent/model mix, recording the rationale inside plan transcripts, todo lists, and MCP manifests so compliance reviewers can trace every decision (FWP-027–FWP-030, FWP-042–FWP-045). The parity checkpoints captured across GitHub Agents tab and VS Code Agent Sessions ensure those records stay aligned regardless of where the task originated, completing the Plan → Implement → Review evidence chain that Phase 3.3 requires (FWP-023–FWP-026, FWP-044–FWP-045).
